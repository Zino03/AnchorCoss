# 빗물받이 막힘 감지 대시보드 — 웹 구현 기획서 (v3, 구현 반영)

> 근거 문서 (이 순서로 기획이 갱신됨)
> 1. `청정강원팀 개발계획서_수정본.hwp` — 최초 기획
> 2. `멘토링 보고서(청정강원).hwp` — 이후 변경사항 (먼저 나온 문서를 덮어씀)
>
> 구현 범위: **웹 대시보드 + 센서 수신 서버(로컬, SQLite)**. 모바일 앱·펌웨어 제외. 센서는 **로드셀 2개** (수위 감지는 폐기).
>
> **v2 → v3 변경 요약**: 서버·DB를 "사용하지 않음"에서 **로컬 수신 서버 + SQLite로 변경**(3.2), 기상청 연동 완료·대상 지역 확정(7장), 실시간/시뮬레이션 모드 도입(3장), 구현 현황 반영(6·9장), 남은 확인 사항 갱신(10장).

## 1. 프로젝트 개요

| 항목 | 내용 |
|---|---|
| 팀 | 청정강원(coss) x 햄버거(앵커) |
| 작품명 | 빗물받이 막힘 감지를 위한 센서 & 오염물 거름망 |
| 주제 | 지역 현안 해결형 |
| 목적 | 낙엽·담배꽁초 등으로 빗물받이가 막히는 것을 거름망으로 1차 차단하고, 센서로 쓰레기 적재를 감지해 수거 시점을 알려 침수 피해를 사전에 예방 |
| 우리 팀(앵커) 담당 | 판정 로직, 가상 데이터 생성기, 기상 API 연동, 센서 수신 서버·DB, 대시보드 전체, 발표 시연 화면 |

- 전황준: 임계값·속도 기반 로직 설계, 상태 판정, 정확도 검증 및 성능 비교
- 강수빈: 서버·DB, 가상 데이터 생성기, 대시보드 전체, 발표 시연 화면
- 변진호: 기상 API 연동 (임베디드 통신·증폭기 구간은 **이번 범위 제외**)

## 2. 문서 간 변경 이력 (개발계획서 → 멘토링 보고서)

| 항목 | 개발계획서 (먼저) | 멘토링 보고서 (나중, **최종**) | 웹 구현에 미치는 영향 |
|---|---|---|---|
| 센서 | 초음파 / 빗물감지 수위 모듈 / 플로트 스위치 후보 | 수위 감지는 주제에서 벗어남 → **로드셀(무게 감지) 2개로 최종 변경**, 구조물 상단에 거치 | 입력이 "수위(cm)" → **"좌/우 중량(g) 2채널"** |
| 측정 대상 | 빗물받이 내부·노면 수위 | 아치형 바닥 양쪽에 쌓이는 **쓰레기 중량** | 막힘 = 중량 누적 |
| 막힘 판정 원리 | 비가 오는데 수위 변화가 없으면 막힘 | 양쪽 중량이 일정 수준을 넘으면 감지, **쓰레기 수거 기준 중량 설정** | 판정 로직 재설계 (4장) |
| 4상태 판정 | 정상 / 격자 위 막힘 / 하부 막힘 / 침수 위험 | 언급 없음. 수위 센서가 빠져 **하부 막힘·침수 위험은 측정 불가** | 상태 체계 재정의 (4장) |
| 거름망 | 플라스틱 바스켓, 격자 10~20mm | 철망은 시제품 구매 후 볼트 체결, 손잡이는 장바구니형, 방수 바스켓 내장 | 웹과 직접 관련 없음 |
| 일정 | 9월~10월 말 | **11월 첫째 주까지 제작 완료**, 완료 후 실험 | 하드웨어 완성 전이므로 **가상 데이터로 먼저 개발** |

## 3. 시스템 구성

```
[ 가상 데이터 생성기 ] ────────────────┐
                                        ├─▶ [ 판정 로직(브라우저) ] ─▶ [ 대시보드 ]
[ 센서 ] ─HTTP POST─▶ [ 수신 서버 ] ─▶ [ SQLite ] ─(3초 폴링)─┘            ▲
 (LoRa면 수신기→변환기 경유)  (로컬)                                         │
[ 기상청 초단기실황 ] ─▶ [ /api/weather (10분 캐시) ] ───────────────────────┘ 강우
```

- 개발계획서 원칙: **실측과 가상 데이터를 동일 처리 경로로 통합**, 하드웨어 완성 전부터 전체 파이프라인 개발·검증.
- 센서 입력을 하나의 샘플 포맷으로 통일해, 실물 로드셀 데이터가 들어와도 판정·화면 코드는 바꾸지 않는다.

### 3.0 데이터 모드 (상단바 전환)

| 모드 | 강우 | 빗물받이 #1 (실물 지점) | 나머지 지점 |
|---|---|---|---|
| **시뮬레이션** (기본) | 시나리오 강우 또는 수동 슬라이더 | 가상 | 가상 |
| **실시간** | 기상청 실측 (10분 갱신) | **서버에 수신된 센서 데이터** | 가상 |

- 실시간 모드에서 실물 데이터가 없으면 #1은 가짜를 만들지 않고 **"점검 필요(수신 기록 없음)"**으로 표시한다.
- 실물 지점은 **실제 시계**로, 가상 지점은 시뮬레이터 시계(실제보다 빠름)로 판정한다. 두 시계를 섞으면 실물 지점이 항상 통신 두절로 보이기 때문.

### 3.1 샘플 데이터 모델 (개발계획서 DB 스키마 기반, 로드셀 2개로 조정)

| 필드 | 설명 | 출처 |
|---|---|---|
| `stationId` | 지점 ID | 센서 |
| `ts` | 측정 시각 (epoch ms). 없으면 서버 수신 시각 | 센서 |
| `leftG`, `rightG` | 좌/우 로드셀 중량(g). `null`=채널 누락, 음수=센서 이상 | 센서 |
| `rainMm` | 강우량(mm/h) — 센서는 보내지 않고 **서버가 수신 시점의 기상청 값을 붙임** | 기상청 |
| `rssi` | 통신 신호 세기 | 센서 (가상 지점은 생성) |
| `batteryPct` | 배터리 잔량 | 센서 (가상 지점은 생성) |

판정 결과(`state`, `score`, `reason`, `flags`)는 샘플에서 계산해 화면에 전달한다 (DB에는 저장하지 않음).

### 3.2 서버·DB — **구현함: 로컬 수신 서버 + SQLite** (v2의 "사용하지 않음"에서 변경)

**변경 이유**: 서버·DB가 없으면 실물 센서 값이 대시보드로 들어오는 경로가 없어 종단 간(센서 → 서버 → 화면) 연동과 합동 테스트가 불가능하고, 새로고침하면 이력이 사라진다.

**구성**
- Node 내장 `node:sqlite`(Node 22.13+)에 저장. `npm run dev` 하나로 화면과 서버가 같이 뜬다.
- **파일 DB라서 Vercel 같은 서버리스에서는 동작하지 않는다.** 센서 연동은 **시연 노트북에서 로컬 실행**이 전제 (Vercel 배포본은 시뮬레이션 모드만 동작).
- DB 접근은 `server/db.js` 한 곳에 모아 두었다 (나중에 DB 교체 시 이 파일만 수정).

**API**
```
POST /api/sensor-data      헤더 x-device-token: <DEVICE_TOKEN>
  본문: { "stationId": "st-1", "ts": 1730000000000, "leftG": 312, "rightG": 287, "rssi": -58, "batteryPct": 91 }
        또는 위 객체의 배열 (재전송용, 최대 500건)
GET  /api/stations                       지점 목록 + 최근 샘플
GET  /api/stations?id=st-1&since=<ms>    since 이후 측정분 (초기 로드)
GET  /api/stations?id=st-1&afterId=<n>   n 이후 저장분 (폴링)
GET  /api/weather                        기상청 실황 프록시
```

**스키마** (개발계획서의 지점 ID·시각·측정값·강우량·신호 세기·배터리·시각/지점 인덱스를 로드셀 기준으로 변경)
```sql
stations(id PK, name, lat, lng, created_at)
samples(id PK, station_id FK, ts, received_at, left_g, right_g, rain_mm, rssi, battery_pct,
        UNIQUE(station_id, ts))   -- + 인덱스 (station_id, ts)
```

**설계 규칙**
- 센서 이상값(음수·`null`)은 거절하지 않고 **그대로 저장** → 판정에서 "점검 필요" 처리. 형식 오류(숫자가 아님, 필수 필드 없음)만 거절.
- 같은 (지점, 시각, 값)의 재전송은 중복 무시. 같은 시각에 값이 다르면 1ms씩 밀어 보관.
- 측정 시각이 1분 넘게 미래이거나 하루보다 오래되면 수신 시각으로 대체 (기기 시계 오류 대비).
- 인증: 기기 공용 토큰(`DEVICE_TOKEN`, `.env.local`). 같은 네트워크 누구나 토큰만 알면 보낼 수 있으므로 외부 인터넷 공개 시에는 재검토.
- 새로고침 시 서버의 최근 1시간 이력으로 복원하며, 이때 **과거 상태 전환은 알림으로 재생하지 않는다.**

**계획서 대비 제외·후속**: 판정 단계·판정 근거의 DB 저장, 일자별 통계 API(`/stats/daily`), API 접근 로그 → **후속 단계**. (판정 로직 `judge.js`가 순수 JS라 서버로 옮기기 쉽다.)

## 4. 판정 로직 (수위 센서 제거 반영)

### 4.1 입력과 한계
- 입력: **좌/우 로드셀 중량**, **강우량**, 통신 상태(마지막 수신 시각).
- 알 수 있는 것: 거름망에 쌓인 쓰레기 **총량**, **좌우 편중**, **증가 속도**.
- 알 수 없는 것: 하수관 하부 막힘, 실제 수위 → 계획서의 "하부 막힘 / 침수 위험" 상태는 **삭제**한다.
- 아치형 바닥이라 쓰레기가 양쪽으로 갈라지므로, 합계만이 아니라 **한쪽만 과적**인 경우도 위험으로 본다 (멘토링: "양쪽에 중량이 일정 수준을 넘으면 감지").

### 4.2 파생 값
| 값 | 정의 |
|---|---|
| `totalG` | `leftG + rightG` |
| `maxSideG` | `max(leftG, rightG)` |
| `imbalance` | `abs(leftG - rightG) / totalG` (총량이 `IMBALANCE_MIN_G` 이상일 때만 계산, 최근 3샘플 중앙값 사용) |
| `rateGPerMin` | 최근 `RATE_WINDOW_MIN`분 최소제곱 기울기로 구한 `totalG` 증가 속도 |
| `raining` | `rainMm ≥ RAIN_MM_H` |

### 4.3 상태 체계

| 상태 | 의미 | 조건 | 화면 색 |
|---|---|---|---|
| **정상** | 적재 거의 없음 | `totalG < WARN_TOTAL_G` | 초록 |
| **주의** | 적재 진행 중 | `WARN_TOTAL_G ≤ totalG < DANGER_TOTAL_G` 이고 `maxSideG < DANGER_SIDE_G` | 노랑 |
| **위험 (수거 필요)** | 수거 기준 초과 | `totalG ≥ DANGER_TOTAL_G` 또는 `maxSideG ≥ DANGER_SIDE_G` | 빨강 |
| **점검 필요** | 데이터를 신뢰할 수 없음 | 통신 두절, 또는 센서 이상 | 회색 |

상태와 별개로 판정 근거에 붙는 **보조 플래그**:
| 플래그 | 조건 | 용도 |
|---|---|---|
| 우천 중 | `raining` | 비 오는 중 주의/위험이면 배너 문구를 "우천 중"으로 강조 (막히면 침수 직결) |
| 급증 | `rateGPerMin ≥ RATE_FAST_G_MIN` | "빠르게 쌓이는 중" 근거 표시 |
| 편중 | `imbalance ≥ IMBALANCE_RATIO` | "한쪽에 쏠림" 근거 표시, 거름망 점검 단서 |

**점검 필요 세부**
- 통신 두절: 마지막 수신 후 `STALE_SEC` 초과 (즉시 확정)
- 센서 이상: 한쪽 값이 음수 또는 `MAX_VALID_G` 초과, 또는 한쪽만 값이 없음(채널 누락)
- 점검 필요일 때는 중량 상태를 판정하지 않는다 (막힘 점수 없음).

### 4.4 상태 전이 규칙 (계획서 1차 로직 반영)
1. **디바운싱**: 새 상태 조건이 `DEBOUNCE_SEC` 이상 지속돼야 상태 변경 인정 (순간 충격·물 튐 방지). 첫 판정, 점검 필요에서의 복귀, 통신 두절 진입은 즉시.
2. **이상치 필터**: 직전 채택값 대비 `MAX_JUMP_G`를 넘는 값은 1회 무시, 2회 연속 유지되면 인정.
3. **이벤트·알림은 상태가 바뀔 때만** 발생 (같은 상태에선 반복 알림 없음).
4. **복구 조건(히스테리시스)**: 위험→주의/정상은 기준값의 `RECOVER_RATIO`배 미만일 때 (수거 후 중량이 확 줄어드는 상황). 경계값에서 상태가 깜빡이는 것을 막는다.
5. 점검 필요에서 데이터가 정상 수신되면 즉시 재판정.

### 4.5 막힘 점수와 판정 근거
- **막힘 점수** (0~100): `max(totalG / DANGER_TOTAL_G, maxSideG / DANGER_SIDE_G) × 100` (상한 100). 지점 정렬·우선순위에 사용.
- **판정 근거 문장** (화면 표시용), 예:
  - "총 중량 1,200g — 수거 기준(1,500g)의 80%"
  - "좌측 로드셀 1,050g — 편측 기준(1,000g) 초과"
  - "우천 중(10mm/h) · 최근 10분간 분당 약 90g씩 증가"
  - "마지막 수신 7분 전 — 통신 두절, 점검 필요"

### 4.6 고도화 (여유 시, 미구현)
계획서의 "속도 기반 고도화"를 로드셀에 맞게 변형: **강수량 대비 증가 속도 기준선** 설정 ("이 강수량이면 이 정도 쌓이는 게 정상") 후 기준 초과 시 조기 경고. 수위·배수 속도 기반 4상태 판정은 센서가 없어 **하지 않는다.**

### 4.7 검증 (계획서 6장 기반) — **구현함**
- 가상 시나리오마다 **정답 상태(ground truth)**를 정의해 판정 정확도 측정.
- **단순 임계값만 쓴 방식** vs **제안 방식**의 정확도/오경보 횟수 비교 (`npm run scenario`).
- 결과 (시나리오 8종 × 난수 5회 평균): 제안 방식 정확도 **98.7%** / 단순 방식 99.5%, 잘못된 상태 전환(오경보) 제안 **0회** / 단순 **17.6회**. 정확도가 약간 낮은 것은 상태 확정 전 30초를 지켜보는 의도된 지연 때문.
- ⚠ 이 수치는 **가상 시나리오 기준**이며 실환경 정확도가 아니다 (합동 테스트 후 재측정 필요).

### 4.8 임계값 (임의의 초기값 — `src/config.js`에서 조정)

| 이름 | 값 | 설명 |
|---|---|---|
| `WARN_TOTAL_G` | 600 | 주의 기준 (총 중량, g) |
| `DANGER_TOTAL_G` | 1500 | 위험·수거 기준 (총 중량, g) |
| `DANGER_SIDE_G` | 1000 | 위험 기준 (한쪽 중량, g) |
| `IMBALANCE_MIN_G` | 300 | 편중 계산을 시작하는 최소 총량 |
| `IMBALANCE_RATIO` | 0.7 | 편중 플래그 기준 (한쪽이 전체의 85% 이상일 때에 해당) |
| `RATE_FAST_G_MIN` | 60 | 급증 플래그 기준 (분당 g) |
| `RATE_WINDOW_MIN` | 10 | 증가 속도 계산 구간 (분) |
| `RAIN_MM_H` | 1 | 우천 판정 기준 (mm/h) |
| `DEBOUNCE_SEC` | 30 | 상태 변경 지속 시간 |
| `MAX_JUMP_G` | 800 | 직전 샘플 대비 이상치 판정 변화량 |
| `RECOVER_RATIO` | 0.8 | 복구 시 기준값 배율 |
| `STALE_SEC` | 300 | 통신 두절 판정 (5분) |
| `MAX_VALID_G` | 5000 | 센서 유효 최대값 |

> 실물 로드셀 보정 후 합동 테스트에서 실제 값으로 교체한다.
> ⚠ **측정 주기에 의존하는 값**: 위 규칙은 샘플이 10초 간격으로 온다고 가정해 튜닝했다. 실제 센서 주기가 1~10분이면 `DEBOUNCE_SEC`·`RATE_*`·`STALE_SEC`을 다시 조정해야 한다 (특히 `STALE_SEC` 5분 < 주기 10분이면 정상 상태도 통신 두절로 판정됨).

## 5. 가상 데이터 생성기 — **구현함**

시나리오(좌/우 중량 곡선 + 강우 + 통신)를 정답 상태와 함께 정의한다.

| 시나리오 | 곡선 | 기대 상태 흐름 |
|---|---|---|
| 정상 | 낮은 값 유지, 소폭 노이즈 | 정상 |
| 서서히 누적 | 좌우 균등하게 선형 증가 | 정상 → 주의 → 위험 |
| 한쪽 쏠림 | 한쪽만 빠르게 증가 | 정상 → 주의 → 위험(편측) + 편중 플래그 |
| 우천 급증 | 강우와 함께 급격히 증가 | 우천 중 + 급증 플래그 |
| 수거 후 복구 | 위험 상태에서 0 근처로 급감 | 위험 → 정상 |
| 통신 두절 | 일정 구간 데이터 누락 | 점검 필요 → 복귀 |
| 센서 이상 | 한쪽 채널 음수/누락 | 점검 필요 |
| 노이즈/충격 | 짧은 스파이크 | 상태 변화 없음 (디바운싱 확인용) |

- 지점: 가상 8곳(청주 충북대 부근 좌표), 지점마다 다른 시나리오. **#1이 실물 센서용**이며 실시간 모드에서 서버 데이터로 대체된다.
- 시연용 제어: 시나리오 선택, 재생/일시정지, 배속(1×/5×/20×), "수거(리셋)", 강우 수동 입력, 시뮬레이션/실시간 전환.
- 샘플 주기: 가상 데이터는 시뮬레이션 10초 간격(실제 1초에 1틱 × 배속). 실제 센서 주기는 10~10분 범위에서 하드웨어팀과 확정 필요.
- `npm run fake-sensor`: 하드웨어 없이 수신 API로 샘플을 보내 서버 경로를 검증하는 센서 흉내.

## 7. 외부 연동 — 기상청 강수 데이터 — **구현함**

- 서비스: 기상청 단기예보 조회서비스의 **초단기실황**(`getUltraSrtNcst`). 1시간 강수량(RN1)을 판정의 강우량(mm/h)으로 사용, 기온·강수 형태·습도·풍속은 화면 표시용.
- **대상 지역: 청주 충북대 부근** (`src/config.js`의 `REGION`). 기상청 격자는 5km 단위라 동네 수준이면 충분. 격자 좌표(68, 106)는 위경도에서 공식 변환식으로 자동 계산.
- 인증키는 `.env.local`의 `KMA_SERVICE_KEY`(서버에서만 사용, 브라우저로 전달 안 됨). 서버가 10분 캐시하고, 기상청 실패 시 직전 값으로 응답.
- 화면: **실시간 모드**에서만 호출. 실패 시 "기상청 연결 실패 + 재시도" 표시, 직전 값이 있으면 ⚠와 함께 유지.
- 키가 없거나 실패해도 **시뮬레이션 모드의 수동 강우 입력**으로 동작하므로 시연은 가능.
- Vercel 배포 시에는 프로젝트 환경변수에 같은 이름으로 키를 따로 넣어야 한다.
- 개발계획서의 기상특보 서비스(`getPwnStatus`)는 **미연동** (필수 아님).

## 10. 남은 확인 사항

1. **하드웨어팀 답변 대기 (5가지)**: ① 측정·전송 주기(시연 시 단축 가능 여부) ② 값의 단위(g 환산값인지 원시값인지) ③ 센서 이상 시 전송값 ④ 통신 방식(Wi-Fi HTTP / LoRa) ⑤ 로드셀 측정 범위·오차·수거 기준 중량
2. **임계값**: 4.8은 임의값 — 실물 보정 후 교체. 물·젖은 쓰레기가 무게에 미치는 영향도 실측 필요
3. **합동 테스트 환경**: 노트북과 센서가 같은 네트워크(와이파이/핫스팟)에 있을 수 있는지, 방화벽 허용
4. **`DEVICE_TOKEN` 전달**: 시연 노트북 `.env.local`의 값을 하드웨어팀(펌웨어 담당)에게 전달해 서버·센서 값 일치시키기
5. **실물 지점 좌표·지점 수**: 현재 지도 좌표는 충북대 부근 임의 배치
6. **브라우저 육안 검증**: 지도 마커·그래프·실시간 모드 동작 (체크리스트는 인수인계 문서 참고)
