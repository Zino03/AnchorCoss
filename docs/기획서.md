# 빗물받이 막힘 감지 대시보드 — 웹 구현 기획서 (초안 v2)

> 근거 문서 (이 순서로 기획이 갱신됨)
> 1. `청정강원팀 개발계획서_수정본.hwp` — 최초 기획
> 2. `멘토링 보고서(청정강원).hwp` — 이후 변경사항 (먼저 나온 문서를 덮어씀)
>
> 구현 범위: **웹 기반 대시보드만** (모바일 앱·펌웨어 제외). 센서는 **로드셀 2개** (수위 감지는 폐기).

---

## 1. 프로젝트 개요

| 항목 | 내용 |
|---|---|
| 팀 | 청정강원(coss) x 햄버거(앵커) |
| 작품명 | 빗물받이 막힘 감지를 위한 센서 & 오염물 거름망 |
| 주제 | 지역 현안 해결형 |
| 목적 | 낙엽·담배꽁초 등으로 빗물받이가 막히는 것을 거름망으로 1차 차단하고, 센서로 쓰레기 적재를 감지해 수거 시점을 알려 침수 피해를 사전에 예방 |
| 우리 팀(앵커) 담당 | 판정 로직, 가상 데이터 생성기, 기상 API 연동, 대시보드 전체, 발표 시연 화면 |
| 하드웨어 담당(청정강원) | 거름망 구조 설계·제작, 센서 선정·설치, 배선 (실물 제작 및 시연은 별도 팀) |

개발계획서의 앵커 팀 역할 중 **이번 웹 구현에 해당하는 것**:
- 전황준: 임계값·속도 기반 로직 설계, 상태 판정, 정확도 검증 및 성능 비교
- 강수빈: 서버·DB, 가상 데이터 생성기, 대시보드 전체, 발표 시연 화면
- 변진호: 기상 API 연동 (임베디드 통신·증폭기 구간은 **이번 범위 제외**)

## 2. 문서 간 변경 이력 (개발계획서 → 멘토링 보고서)

| 항목 | 개발계획서 (먼저) | 멘토링 보고서 (나중, **최종**) | 웹 구현에 미치는 영향 |
|---|---|---|---|
| 센서 | 초음파 / 빗물감지 수위 모듈 / 플로트 스위치 후보 | 수위 감지는 주제에서 벗어남 → **로드셀(무게 감지) 2개로 최종 변경**, 구조물 상단에 거치 | 입력이 "수위(cm)" → **"좌/우 중량(g) 2채널"** |
| 측정 대상 | 빗물받이 내부·노면 수위 | 아치형 바닥 양쪽에 쌓이는 **쓰레기 중량** | 막힘 = 중량 누적 |
| 막힘 판정 원리 | 비가 오는데 수위 변화가 없으면 막힘 | 양쪽 중량이 일정 수준을 넘으면 감지, **쓰레기 수거 기준 중량 설정** | 판정 로직 재설계 (4장) |
| 4상태 판정 | 정상 / 격자 위 막힘 / 하부 막힘 / 침수 위험 | 언급 없음. 수위 센서가 빠져 **하부 막힘·침수 위험은 측정 불가** | 상태 체계 재정의 (4장) |
| 거름망 | 플라스틱 바스켓, 격자 10~20mm | 철망은 시제품 구매 후 볼트 체결, 손잡이는 장바구니형, 방수 바스켓 내장 | 웹과 직접 관련 없음 |
| 일정 | 9월~10월 말 | **11월 첫째 주까지 제작 완료**, 완료 후 실험 | 하드웨어 완성 전이므로 **가상 데이터로 먼저 개발** |

## 3. 시스템 구성 (웹 한정)

```
[가상 데이터 생성기] ─┐
 (실물 연결 시 같은    ├─▶ [판정 로직] ─▶ [대시보드(웹)]
  포맷으로 교체 가능)   │       ▲
[기상청 강수 API] ─────┘       └─ 임계값 설정(config)
```

- 개발계획서 원칙: **실측과 가상 데이터를 동일 처리 경로로 통합**, 하드웨어 완성 전부터 전체 파이프라인 개발·검증.
- 센서 입력을 하나의 샘플 포맷으로 통일해, 실물 로드셀 데이터가 들어와도 판정·화면 코드는 바꾸지 않는다.

### 3.1 샘플 데이터 모델 (개발계획서 DB 스키마 기반, 로드셀 2개로 조정)

| 필드 | 설명 | 출처 |
|---|---|---|
| `stationId` | 지점 ID | 계획서 |
| `ts` | 측정 시각 | 계획서 |
| `leftG`, `rightG` | 좌/우 로드셀 중량(g) — *계획서의 "수위 값"을 대체* | 멘토링 |
| `rainMm` | 강우량(mm/h) | 계획서 (기상청) |
| `rssi` | 통신 신호 세기 | 계획서 (가상 생성) |
| `batteryPct` | 배터리 잔량 | 계획서 (가상 생성) |

판정 결과(`state`, `score`, `reason`, `flags`)는 샘플에서 계산해 화면에 전달한다.

### 3.2 서버·DB — 결론: **필수 아님, 이번엔 사용하지 않음**
- 이유: 시연·대회용이고, 센서 실물이 아직 없어 데이터는 브라우저에서 생성한다. 이력 그래프는 화면이 열려 있는 동안의 메모리 데이터로 충분하다.
- 기상청 인증키를 숨기기 위한 **서버리스 함수 1개(`/api/weather`)만** 사용한다. (키 발급 후)
- 계획서의 DB 항목(SQLite 스키마, 인증 토큰, API 로그)은 **이번 범위에서 제외**한다.
- 단, **대회 전 실물 센서와 합동 테스트**를 할 때 실제 데이터를 웹으로 받아야 하면 수신 엔드포인트(`POST /api/sensor-data`)가 필요하다. 그때 메모리 저장 수준의 최소 구현을 **추가**한다(샘플 포맷이 같아서 판정·화면 변경 없음). 하드웨어팀의 전송 방식(Wi-Fi/HTTP 등)은 합동 테스트 전 확인 필요.

## 4. 판정 로직 (수위 센서 제거 반영)

### 4.1 입력과 한계
- 입력: **좌/우 로드셀 중량**, **강우량**, 통신 상태(마지막 수신 시각).
- 알 수 있는 것: 거름망에 쌓인 쓰레기 **총량**, **좌우 편중**, **증가 속도**.
- 알 수 없는 것: 하수관 하부 막힘, 실제 수위 → 계획서의 "하부 막힘 / 침수 위험" 상태는 **삭제**한다.
- 아치형 바닥이라 쓰레기가 양쪽으로 갈라지므로, 합계만이 아니라 **한쪽만 과적**인 경우도 위험으로 본다 (멘토링: "양쪽에 중량이 일정 수준을 넘으면 감지").

### 4.2 파생 값
| 값 | 정의 |
|---|---|
| `totalG` | `leftG + rightG` |
| `maxSideG` | `max(leftG, rightG)` |
| `imbalance` | `abs(leftG - rightG) / totalG` (총량이 `IMBALANCE_MIN_G` 이상일 때만 계산) |
| `rateGPerMin` | 최근 N분 이동 평균 기준 `totalG` 증가 속도 |
| `raining` | `rainMm ≥ RAIN_MM_H` |

### 4.3 상태 체계 (신규)

| 상태 | 의미 | 조건 | 화면 색 |
|---|---|---|---|
| **정상** | 적재 거의 없음 | `totalG < WARN_TOTAL_G` | 초록 |
| **주의** | 적재 진행 중 | `WARN_TOTAL_G ≤ totalG < DANGER_TOTAL_G` 이고 `maxSideG < DANGER_SIDE_G` | 노랑 |
| **위험 (수거 필요)** | 수거 기준 초과 | `totalG ≥ DANGER_TOTAL_G` 또는 `maxSideG ≥ DANGER_SIDE_G` | 빨강 |
| **점검 필요** | 데이터를 신뢰할 수 없음 | 통신 두절, 또는 센서 이상 | 회색 |

상태와 별개로 판정 근거에 붙는 **보조 플래그**:
| 플래그 | 조건 | 용도 |
|---|---|---|
| 우천 중 | `raining` | 비 오는 중 주의/위험이면 배너 문구를 "우천 중"으로 강조 (막히면 침수 직결) |
| 급증 | `rateGPerMin ≥ RATE_FAST_G_MIN` | "빠르게 쌓이는 중" 근거 표시 |
| 편중 | `imbalance ≥ IMBALANCE_RATIO` | "한쪽에 쏠림" 근거 표시, 거름망 점검 단서 |

**점검 필요 세부**
- 통신 두절: 마지막 수신 후 `STALE_SEC` 초과
- 센서 이상: 한쪽 값이 음수 또는 `MAX_VALID_G` 초과, 또는 한쪽만 값이 없음(채널 누락)
- 점검 필요일 때는 중량 상태를 판정하지 않고 마지막 정상 상태를 참고로만 표시한다.

### 4.4 상태 전이 규칙 (계획서 1차 로직 반영)
1. **디바운싱**: 새 상태 조건이 `DEBOUNCE_SEC` 이상 지속돼야 상태 변경 인정 (순간 충격·물 튐 방지).
2. **이상치 필터**: 직전 샘플 대비 변화율이 `MAX_JUMP_G`를 넘는 값은 일시 노이즈로 보고 무시 (단, 연속으로 유지되면 인정).
3. **이벤트·알림은 상태가 바뀔 때만** 발생 (같은 상태에선 반복 알림 없음).
4. **복구 조건(히스테리시스)**: 위험→주의/정상은 기준값의 `RECOVER_RATIO`배 미만이 `DEBOUNCE_SEC` 이상 지속될 때 (수거 후 중량이 확 줄어드는 상황). 경계값에서 상태가 깜빡이는 것을 막는다.
5. 점검 필요에서 데이터가 정상 수신되면 즉시 재판정.

### 4.5 막힘 점수와 판정 근거
- **막힘 점수** (0~100): `max(totalG / DANGER_TOTAL_G, maxSideG / DANGER_SIDE_G) × 100` (상한 100). 지점 정렬·우선순위에 사용.
- **판정 근거 문장** (화면 표시용), 예:
  - "총 중량 1,200g — 수거 기준(1,500g)의 80%"
  - "우측 로드셀 1,050g — 편측 기준(1,000g) 초과"
  - "우천 중 · 최근 10분간 분당 약 90g씩 증가"
  - "마지막 수신 7분 전 — 통신 두절, 점검 필요"

### 4.6 고도화 (여유 시)
계획서의 "속도 기반 고도화"를 로드셀에 맞게 변형: **강수량 대비 증가 속도 기준선** 설정 ("이 강수량이면 이 정도 쌓이는 게 정상") 후 기준 초과 시 조기 경고. 수위·배수 속도 기반 4상태 판정은 센서가 없어 **하지 않는다.**

### 4.7 검증 (계획서 6장 기반)
- 가상 시나리오마다 **정답 상태(ground truth)**를 미리 정의해 판정 정확도 측정.
- **단순 임계값만 쓴 방식**(디바운싱·히스테리시스·편중 판정 없음) vs **제안 방식**의 정확도/오경보 횟수 비교표 작성 (`npm run scenario`로 출력).

### 4.8 임계값 (임의의 초기값 — `src/config.js`에서 조정)

| 이름 | 값 | 설명 |
|---|---|---|
| `WARN_TOTAL_G` | 600 | 주의 기준 (총 중량, g) |
| `DANGER_TOTAL_G` | 1500 | 위험·수거 기준 (총 중량, g) |
| `DANGER_SIDE_G` | 1000 | 위험 기준 (한쪽 중량, g) |
| `IMBALANCE_MIN_G` | 300 | 편중 계산을 시작하는 최소 총량 |
| `IMBALANCE_RATIO` | 0.7 | 편중 플래그 기준 (한쪽이 전체의 85% 이상일 때에 해당) |
| `RATE_FAST_G_MIN` | 60 | 급증 플래그 기준 (분당 g) |
| `RAIN_MM_H` | 1 | 우천 판정 기준 (mm/h) |
| `DEBOUNCE_SEC` | 30 | 상태 변경 지속 시간 |
| `MAX_JUMP_G` | 800 | 직전 샘플 대비 이상치 판정 변화량 |
| `RECOVER_RATIO` | 0.8 | 복구 시 기준값 배율 |
| `STALE_SEC` | 300 | 통신 두절 판정 (5분) |
| `MAX_VALID_G` | 5000 | 센서 유효 최대값 |

> 실물 로드셀 보정 후 합동 테스트에서 실제 값으로 교체한다.

## 5. 가상 데이터 생성기

시나리오(좌/우 중량 곡선 + 강우 + 통신)를 정답 상태와 함께 정의한다.

| 시나리오 | 곡선 | 기대 상태 흐름 |
|---|---|---|
| 정상 | 낮은 값 유지, 소폭 노이즈 | 정상 |
| 서서히 누적 | 좌우 균등하게 선형 증가 | 정상 → 주의 → 위험 |
| 한쪽 쏠림 | 한쪽만 빠르게 증가 | 정상 → 주의 → 위험(편측) + 편중 플래그 |
| 우천 급증 | 강우와 함께 급격히 증가 | 우천 중 + 급증 플래그 |
| 수거 후 복구 | 위험 상태에서 0 근처로 급감 | 위험 → 정상 |
| 통신 두절 | 일정 구간 데이터 누락 | 점검 필요 → 복귀 |
| 센서 이상 | 한쪽 채널 음수/고정 | 점검 필요 |
| 노이즈/충격 | 짧은 스파이크 | 상태 변화 없음 (디바운싱 확인용) |

- 지점: 실물 센서 1지점 + 가상 지점 다수를 함께 표시 (실물 연결 전에는 모두 가상, 지점마다 다른 시나리오).
- 시연용 제어: 시나리오 선택, 재생/일시정지, 속도 배율, "수거(리셋)" 버튼, 강우 수동 입력.
- 샘플 주기: 시연에서는 몇 초 단위로 가속 (실제 센서는 1~10분, 계획서 기준).

## 6. 대시보드 화면 (계획서 5장 기반, 웹 한정)

| # | 기능 | 우선순위 |
|---|---|---|
| 1 | 지점별 상태 목록 + 지도 UI (4상태 색 구분), 자동 새로고침 | **필수** |
| 2 | 이력 그래프 — 시간별 좌/우/합계 중량, 기준선 표시 | **필수** |
| 3 | 판정 근거 표시 영역 (4.5의 문장) | **필수** |
| 4 | 위험 알림 — **화면 배너/토스트** (이메일·문자 제외) | **필수** |
| 5 | 통신 상태 — 마지막 통신 시각, 신호세기, 배터리, 두절 시 "점검 필요" | **필수** |
| 6 | 좌/우 로드셀 시각화 (아치형 바닥에 쌓인 정도를 좌우 게이지로) | 권장 |
| 7 | 상태 전환 타임라인 (위험 도달·수거 이력) | 권장 |
| 8 | 수거 우선순위 목록 (막힘 점수 + 우천 여부 기준 정렬) | 권장 |
| 9 | 일자별 통계 (위험 도달 횟수·지속시간) | 여유 시 |
| 10 | 시연 제어 패널 (시나리오·재생·리셋) | **필수** (시연용) |

- 웹 한정이므로 반응형은 기본 수준만 고려 (네이티브 앱·푸시 제외).
- 상태는 색뿐 아니라 텍스트·아이콘으로도 표시 (색각 접근성).

## 7. 외부 연동 — 기상청 강수 데이터

- 계획서: 기상청 강우 데이터 공공 API 연동, 센서와 동일 처리 경로로 통합.
- 용도: `rainMm`을 판정(우천 플래그)과 화면(우천 중 강조)에 반영.
- **인증키·대상 지역은 팀원에게 받아오는 중 → 현재 비워둠** (`.env.local`의 `KMA_SERVICE_KEY`, `src/config.js`의 지역 좌표/격자).
- 키가 없는 동안은 **시뮬레이터의 수동 강우 입력**으로 동작하므로, 키 없이도 전체 개발·시연이 가능하다.

## 9. 구현 순서 (제안)

5. 권장 기능 (좌우 게이지, 타임라인, 우선순위 목록)
6. 기상청 API 연동 (키 수령 후)
7. 합동 테스트 대비: 실물 데이터 수신 엔드포인트 최소 구현 (필요 시)
